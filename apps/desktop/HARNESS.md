# Recursive Codex harness

## Status

The complete v2 graph, additive migration v29, recovery barriers, and shutdown
protocol are wired into the desktop gateway. New harness admission requires an
opaque capability minted by the exact live dynamic-tool lifecycle probe for
the current signed-in account, pinned app-server binary, and process
generation. The capability is process-local, cannot be serialized, and dies
when any binding changes. Release-bound laws cover HRA's bounded-program and
recursive-actor semantics. They do not claim provider behavior.

Signed semantic-evidence custody is dormant. The production graph does not
load its inbox, construct its custody service, or let it grant authority. The
harness still requires the definitive current-tree gate and a current-binary
smoke before a supported distribution. No held-out A-E evaluation has run,
so the harness is experimental and makes no claim that it outperforms plain
Codex.

The adaptive optimizer has a pure Phase 0 research boundary only. It can parse
and digest one registry-keyed frozen finite benchmark, build block-balanced
pair assignments, and recompute them only with live assignment-key custody
before calculating conservative quality and resource gates from exact fixtures.
Even a complete result carries `policyAuthorization = none` and
`rolloutAuthorization = none`. No benchmark registry, evaluator runner,
persistence, provider effect, live trial, canary, acceptance, rollback, or
renderer control is wired into the production graph.

Codex remains the only model and transcript runtime. HRA owns only the
closed lexical RLM v2 program boundary, context references, encrypted local
state, actor receipts, inherited budgets, and reconciliation. It never falls
back to a reusable CLI, SDK, socket bearer, or raw provider RPC.

HRA's goal is to be the tokenmaxxing metaharness for Codex. In this document,
that means using multiple configured Codex subscriptions and durable parallel
sessions deliberately, while keeping provider authority on the paired Mac. It
does not mean claiming a measured speed, quality, or token-cost advantage. The
policy is experimental and remains subject to held-out evaluation.

## Model and acceleration policy

- **Sol Max is the default.** Ordinary panes and standard metaharness work use
  Sol Max unless a durable work class selects another profile.
- **Sol Ultra is for wide work.** Large changesets and broad research can use
  Sol Ultra when parallelism or deeper planning makes that lane appropriate.
- **Luna Max is for bounded leaves.** Clearly defined, trivial, or narrow work
  can use Luna Max. If Luna is unavailable, HRA records the closed fallback to
  Sol Max rather than silently changing an active actor.
- **Fast is a sparse per-turn overlay.** Automatic Fast is limited to a root
  task's critical-path turn when reasoning or file generation is the
  bottleneck. It has one durable reservation, never changes the actor's model
  or effort, and falls back to Standard when its capability or reservation is
  unavailable. Manual Fast controls on ordinary panes remain separate.
- **Continuity is part of routing.** Actor lineage, bounded visible history,
  stable context references, and cache-compatible instruction prefixes are
  retained across turns where the provider supports them. HRA records the
  requested and observed profile so a recovery can prove what actually ran.

## Accepted v1 behavior

- Ordinary Codex panes start on GPT-5.6 Sol at Max reasoning. Recursive work may
  select a narrower execution profile, while the actor's model and effort stay
  fixed for its incarnation. Fast is a per-turn acceleration, never an actor
  identity. The default `criticalPath` policy may request it only for recursive
  turns that are both on the root task's critical path and bottlenecked by
  inference or output generation. Turning automatic Fast Off leaves every
  ordinary pane's manual Fast control unchanged.

- A parsed, bounded lexical RLM v2 AST supplies variables, lexical bindings,
  conditionals, bounded iteration, bounded parallel branches, and only adopted
  context, heap, and actor operations. It cannot evaluate gateway JavaScript,
  choose a provider, account, or root, widen authority, or call arbitrary RPC.
- A context handle indexes the provider-visible completed prefix and binds the
  current input only after two complete, stable, same-generation paginated
  scans agree on exact canonical evidence. Compaction, attachments, structured
  input, ambiguous assistant phase, truncation, or any unrepresentable content
  returns typed partial or unavailable with no admitted items. Explicit
  retained values are encrypted, chunked objects below Application Support;
  their metadata is content-free and their installation master remains in
  Keychain. HRA never inspects `CODEX_HOME` for context.
- Every actor incarnation uses provider `thread/start`, never `thread/fork`.
  `agent.spawn` persists the relationship, decreasing budget, lane, and
  prepared attempt before returning a handle. An idle child may receive a later
  `agent.send` only by a new provider `turn/start`, never `turn/steer`.
- `status`, `waitAny`, `waitAll`, `result`, and `cancel` use durable receipts
  and proof-bearing reconciliation. Ambiguous provider mutations are never
  replayed. The UI retains per-child Open and Stop controls.
- A durable session binding separates the incarnation's immutable admission
  generation from its current observed runtime generation. Restart recovery
  double-scans exact provider history before advancing that binding. Provider
  mutations keep their original generation fence while later reads use the
  proven successor generation.
- A token-usage fact may arrive before its provider turn binds. Migration v29
  stores that fact in an identity-bound inbox and consumes it exactly once
  after binding. Unknown or conflicting attribution fails closed.
- Definitive post-admission quota exhaustion may continue one logical turn on
  an unvisited configured subscription. HRA captures bounded visible
  history, opens a fresh thread, verifies exact history injection, and sends
  the literal `continue` once. Every stage has a durable CAS receipt, including
  N to N+1 to N+2 recovery. Missing history, unstable readback, ambiguous
  dispatch, or account reuse stops the handoff.
- Dynamic provider callbacks remain routable during boot and shutdown, but
  program admission stays closed until every context, proposal, root, actor,
  session, liveness, program, RLM, projection, and renderer recovery barrier
  has completed. Shutdown synchronously closes host admission, joins every
  accepted chat and harness producer, stops account runtimes, closes provider
  sources, joins their terminal tails, and only then permits SQLite to close.
- The exact live probe is the only current provider capability authority. Its
  witness digest is the immutable evidence-object digest produced by that
  probe, and every call is rebound to the live account, binary, generation,
  thread, turn, request instance, owner, settings, context witness, and budget.
  Mutable files, SQLite rows, stale capabilities, and dormant signed evidence
  cannot enable admission.
- The proposal policy is Off or Suggest. Suggest records one immutable proposal
  and never changes the proposing session or any runtime policy.

## Explicit v1 exclusions

v1 has no goals, heartbeats, evaluation runs, trials, canary, activation,
rollback, proposal data preview, proposal deletion, or autonomous Git
publication. The research-only Phase 0 optimizer schemas do not add those
capabilities. v1 also has no provider fork or steering path. Future export,
cross-device heap sync, or lifecycle data-management controls need a separate
accepted design and exact authority review.
